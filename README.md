# sunfire

Мостовой шлюз. Клиент терминирует SOCKS5 на петле, заворачивает каждую сессию в отдельный
AEAD-поток и уносит на шлюз; шлюз распаковывает поток и открывает соединение к цели уже от
своего адреса. Для цели источник трафика — шлюз.

```
   127.0.0.1:1080                                        exit
        │                                                  ▲
   ┌────┴────┐   salt ‖ ChaCha20-Poly1305 frames    ┌───────┴───────┐
   │ sunfire │ ═══════════ tcp | udp (kcp) ════════ │   sunfired    │
   └────┬────┘                                      └───────┬───────┘
        │ socks5                                            │ dial
   приложение                                             цель
```

Ключи разводятся HKDF-SHA256 по направлениям, токен по проводу не ходит, кадры набиваются
до плавающей длины. Ни TUN, ни root, ни правки маршрутизации — обычный процесс со
слушателем на петле.

Одна SOCKS-сессия — одно соединение до шлюза, без мультиплексора: нагрузка сама
раскладывается по ядрам. Транспорта два, TCP и UDP поверх KCP; клиент умеет замерить оба и
сесть на тот, что быстрее на этом маршруте.

Две части: **`sunfired`** — сервер, **`sunfire`** — клиент.

# Сервер

## Установка

### Пакет

```bash
curl -LO https://github.com/redsawah/sunfire/releases/latest/download/sunfired_0.2.2_amd64.deb
sudo dpkg -i sunfired_0.2.2_amd64.deb
```

Кладёт `/usr/bin/sunfired`, юнит `/lib/systemd/system/sunfired.service` и пример конфига
`/etc/sunfire/main.conf.example`.

### Докер

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
cp main.conf.example main.conf   # или напишите свой, см. ниже
docker compose up -d
docker compose logs -f
```

Конфиг пробрасывается томом и правится снаружи контейнера:

```yaml
volumes:
  - ./main.conf:/etc/sunfire/main.conf:ro
```

Сеть хостовая — иначе за NAT контейнера все клиенты выглядели бы с одного адреса, и
привязка по адресу теряет смысл.

Образ собирается под ту архитектуру, где вы его собираете. Если собираете на arm-машине,
а сервер x86:

```bash
docker build --platform linux/amd64 -t sunfire/sunfired .
```

### Из исходников

Нужен Go 1.26+.

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
go build -o sunfired ./cmd/sunfired
sudo install -m755 sunfired /usr/bin/
```

## Настройка

Токен на каждого клиента:

```bash
sunfired -token
```

`/etc/sunfire/main.conf`:

```json
{
  "listen": {
    "tcp": ":9000",
    "udp": ":9000"
  },
  "users": [
    { "name": "node-a", "token": "ВАШ-ТОКЕН" }
  ]
}
```

| поле | что |
|---|---|
| `listen` | транспорт → адрес. Ключи только `tcp` и `udp`, хотя бы один |
| `status_addr` | адрес статуса для монитора, только петля. По умолчанию `127.0.0.1:9601` |
| `pin_client_ip` | закрепить токен за первым адресом, с которого им воспользовались. Привязка в памяти, снимается рестартом |
| `users[].name` | имя, обязательное и непустое |
| `users[].token` | токен, минимум 16 символов, не повторяется между пользователями |
| `users[].client_ips` | с каких адресов принимать этот токен: IP и/или подсети `10.0.0.0/8`. Пусто — откуда угодно |
| `users[].disabled` | выключить, не удаляя |

Оба поля про адрес **клиента**. Куда клиенту ходить, сервер не ограничивает — он получает
весь интернет.

Конфиг читается один раз при старте: поменяли — перезапустите.

TCP и UDP могут висеть на одном номере порта, это разные сокеты. В фаерволе откройте порт
**и по TCP, и по UDP**.

## Запуск

```bash
sudo systemctl enable --now sunfired
journalctl -u sunfired -f
```

Флаги:

| флаг | по умолчанию | что |
|---|---|---|
| `-config` | `/etc/sunfire/main.conf` | путь к конфигу |
| `-token` | — | напечатать новый токен и выйти |
| `-top` | — | открыть монитор |
| `-version` | — | напечатать версию и выйти |
| `-check-update` | — | проверить наличие новой версии и выйти |
| `-update` | — | обновиться до последней версии и выйти |

# Клиент

## Установка

### Пакет

```bash
curl -LO https://github.com/redsawah/sunfire/releases/latest/download/sunfire_0.2.2_amd64.deb
sudo dpkg -i sunfire_0.2.2_amd64.deb
```

Кладёт `/usr/bin/sunfire`, юнит `/lib/systemd/system/sunfire.service` и пример
`/etc/sunfire/client.env.example`.

### Из исходников

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
go build -o sunfire ./cmd/sunfire
sudo install -m755 sunfire /usr/bin/
```

## Запуск

Разово:

```bash
sunfire -gw СЕРВЕР:9000 -token ВАШ-ТОКЕН -socks 127.0.0.1:1080
```

Службой — впишите адрес и токен в `/etc/sunfire/client.env`:

```
GW=СЕРВЕР:9000
TOKEN=ВАШ-ТОКЕН
SOCKS=127.0.0.1:1080
```

```bash
sudo systemctl enable --now sunfire
journalctl -u sunfire -f
```

Проверка:

```bash
curl -x socks5h://127.0.0.1:1080 https://ifconfig.me    # должен показать адрес сервера
```

По умолчанию `-transport auto`: клиент замеряет каждый транспорт и садится на самый быстрый.

```
замер транспортов…
  tcp  842 Мбит/с, rtt 31ms
  udp  1170 Мбит/с, rtt 29ms
SOCKS5 127.0.0.1:1080 -> СЕРВЕР:9000 (udp)
```

Флаги:

| флаг | по умолчанию | что |
|---|---|---|
| `-gw` | — | адрес сервера `host:port` |
| `-token` | — | токен |
| `-socks` | `127.0.0.1:1080` | адрес SOCKS5, только петля |
| `-transport` | `auto` | `auto`, `tcp` или `udp` |
| `-streams` | `1` | соединений на одну сессию |
| `-probe-time` | `3s` | сколько лить при замере одного транспорта |
| `-v` | выкл | подробный лог |
| `-top` | — | открыть монитор |
| `-status` | `127.0.0.1:9602` | адрес статуса для монитора, только петля |
| `-version` | — | напечатать версию и выйти |
| `-check-update` | — | проверить наличие новой версии и выйти |
| `-update` | — | обновиться до последней версии и выйти |

### Про `-streams`

Одно TCP-соединение упирается в потолок маршрута: на канале с потерями и RTT 38 мс это
около 600 Мбит/с, сколько бы ни было свободной полосы. `-streams N` раскладывает **одну**
сессию по N соединениям и собирает обратно на сервере — одиночная передача перестаёт
упираться в этот потолок.

Нужно это только когда одна сессия должна забрать канал целиком. Если через плечо и так
идёт много одновременных соединений, они раскладываются по ядрам сами, и `-streams` не
нужен — поэтому по умолчанию 1.

# Монитор

В обоих бинарях есть монитор состояния в терминале:

```bash
sunfired -top     # на сервере
sunfire -top      # на клиенте
```

Показывает число сессий и сколько обслужено всего, отдельные графики загрузки и отдачи,
загрузку процессора со средней за 1/5/15 минут, память, таблицу по пользователям (на
клиенте — по хостам назначения) и ленту журнала.

Данные монитор берёт со статуса, который служба поднимает **только на петле**: сервер —
`status_addr` из конфига (по умолчанию `127.0.0.1:9601`), клиент — флаг `-status`
(по умолчанию `127.0.0.1:9602`). Адрес не на петле отвергается: наружу статус не выставляем.

# Как устроен протокол

Одно SOCKS-соединение — одно соединение к серверу, без мультиплексора.

Клиент открывает соединение и первым делом шлёт 32 байта случайной соли открытым текстом.
Дальше обе стороны выводят из соли и токена два независимых подключа —
`HKDF-SHA256(token, salt, "sunfire/1 c2s")` и `…s2c`, по одному на направление, чтобы
счётчики-нонсы не пересекались. Сам токен по проводу не идёт: сервер перебирает свои токены
и берёт тот, которым расшифровался первый кадр.

Дальше всё едет кадрами:

```
[ длина полезного (2) + длина набивки (2) | тег ][ полезное + набивка | тег ]
```

Шифр — ChaCha20-Poly1305, нонс — счётчик, свой на каждое направление, инкремент на каждый
кадр (заголовок и тело считаются отдельно). Полезное — до 16 КиБ. Набивка идёт нулями и на
приёме отбрасывается: первый кадр набивается заметно, дальше редко и мелко, чтобы размеры
кадров не повторяли размеры данных приложения.

Первый кадр от клиента несёт адрес цели, дальше идут данные.

UDP-транспорт даёт надёжный поток через KCP, а каждая датаграмма перед отправкой
запечатывается отдельно: ключ — `HKDF-SHA256(token, "sunfire/1 udp")`, нонс — 12 случайных
байт перед шифротекстом. Заголовки KCP оказываются внутри шифротекста. Битые и чужие
датаграммы молча отбрасываются.

При `-streams N` первый кадр несёт служебную форму `@s <sid> <n> host:port`, остальные
соединения присоединяются кадром `@j <sid> <idx>`. Данные режутся на куски по 64 КиБ и
идут по кругу: кусок k по соединению k mod n, поэтому порядковые номера не нужны — порядок
задаётся позицией.

Замер скорости использует служебный адрес `@probe`: сервер на него никуда не соединяется, а
отражает первую посылку (это RTT) и дальше поглощает поток (это пропускная способность).

# Чего пока нет

- защиты от повтора: записанное начало соединения можно переиграть;
- ограничения на число одновременных соединений с одним токеном;
- UDP ASSOCIATE в SOCKS5 — поддерживается только CONNECT.

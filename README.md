# sunfire

Мостовой шлюз между двумя машинами. Клиент терминирует SOCKS5 на петле, заворачивает
каждую сессию в отдельный AEAD-поток и уносит на сервер; сервер распаковывает поток и
открывает соединение к цели уже от своего адреса. Для цели источник трафика — сервер.

```
   127.0.0.1:1080                                        exit
        │                                                  ▲
   ┌────┴────┐   salt ‖ ChaCha20-Poly1305 frames    ┌───────┴───────┐
   │ sunfire │ ═══════════ tcp | udp (kcp) ════════ │   sunfired    │
   └────┬────┘                                      └───────┬───────┘
        │ socks5                                            │ dial
   приложение                                             цель
```

Ни TUN, ни root, ни правок маршрутизации — обычный процесс со слушателем на петле.
Ставится за минуту, сносится за секунду, системе после себя ничего не оставляет.

Одна SOCKS-сессия — одно соединение до сервера, без мультиплексора. Это не экономия ради
экономии: мультиплексор загнал бы все потоки в одно TCP, а одно TCP на маршруте с потерями
упирается в потолок независимо от ширины канала. Здесь N сессий — это N независимых
цепочек, которые сами раскладываются по ядрам.

Транспорта два: обычный TCP и UDP поверх KCP. Клиент при старте меряет оба и садится на
тот, что быстрее на этом маршруте, а не на тот, что кто-то счёл правильным.

Две части: **`sunfired`** — сервер, **`sunfire`** — клиент.

# Меню

Самое короткое, что нужно знать: почти всё настраивается из меню, а не правкой файлов.

```bash
sudo sunfired -menu     # на сервере
sudo sunfire -menu      # на клиенте
```

Меню нумерованное, ввод построчный — работает по ssh в любом терминале, без перехвата
клавиш и без сюрпризов с раскладкой. Изменения копятся в памяти и попадают на диск только
по пункту «Сохранить»; при выходе с несохранёнными переспросит.

**На сервере:** пользователи (добавить — сразу сгенерирует токен и напечатает готовую
строку для клиента; включить, выключить, удалить, показать токен целиком), лимит машин на
токен, адреса прослушивания, транспортный ключ, привязка к адресу клиента, монитор.

**На клиенте:** серверы и их очередь перехода, локальный SOCKS, транспорт, число
соединений на сессию, монитор.

Конфига ещё нет — меню предложит создать с умолчаниями. Права на файлы `600` и владелец
root, потому что внутри токены, — отсюда `sudo`.

# Сервер

## Установка

### Пакет

```bash
curl -LO https://github.com/redsawah/sunfire/releases/latest/download/sunfired_0.3.4_amd64.deb
sudo dpkg -i sunfired_0.3.4_amd64.deb
```

Кладёт `/usr/bin/sunfired`, юнит `/lib/systemd/system/sunfired.service` и пример конфига
`/etc/sunfire/main.conf.example`.

### Докер

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
cp main.conf.example main.conf   # или напишите свой, см. ниже
docker compose up -d
docker compose logs -f
```

Конфиг пробрасывается томом и правится снаружи контейнера:

```yaml
volumes:
  - ./main.conf:/etc/sunfire/main.conf:ro
```

Сеть хостовая, и это не прихоть: за NAT контейнера все клиенты выглядели бы с одного
адреса, а на адресе завязаны и `client_ips`, и лимит машин.

Образ собирается под ту архитектуру, где вы его собираете. Если собираете на arm-машине,
а сервер x86:

```bash
docker build --platform linux/amd64 -t sunfire/sunfired .
```

### Из исходников

Нужен Go 1.26+.

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
go build -o sunfired ./cmd/sunfired
sudo install -m755 sunfired /usr/bin/
```

## Настройка

Всё то же самое есть в `sudo sunfired -menu`. Если хочется руками —
`/etc/sunfire/main.conf`:

```json
{
  "listen": {
    "tcp": ":9000",
    "udp": ":9000"
  },
  "transport_key": "ТРАНСПОРТНЫЙ-КЛЮЧ",
  "users": [
    { "name": "node-a", "token": "ВАШ-ТОКЕН", "clients": 50 }
  ]
}
```

Отдельный токен, если нужен без меню: `sunfired -token`.

| поле | что |
|---|---|
| `listen` | транспорт → адрес. Ключи только `tcp` и `udp`, хотя бы один |
| `transport_key` | общий ключ шлюза, минимум 16 символов. Нужен только для `udp` и обязателен, если тот включён. Выдаётся всем клиентам этого сервера. Генерируется в меню |
| `status_addr` | адрес статуса для монитора, только петля. По умолчанию `127.0.0.1:9601` |
| `pin_client_ip` | закрепить токен за первым адресом, с которого им воспользовались. Привязка живёт в памяти и снимается рестартом |
| `users[].name` | имя, обязательное и непустое |
| `users[].token` | токен, минимум 16 символов, не повторяется между пользователями |
| `users[].client_ips` | с каких адресов принимать этот токен: IP и/или подсети `10.0.0.0/8`. Пусто — откуда угодно |
| `users[].clients` | лимит машин на токен, см. ниже. `0` — без ограничения |
| `users[].disabled` | выключить, не удаляя |

`client_ips` и `pin_client_ip` — оба про адрес **клиента**. Куда клиенту ходить, сервер не
ограничивает: он получает весь интернет.

### Лимит машин на токен

Под одним токеном может работать сколько угодно машин — состояния «на токен» у сервера
нет, каждое соединение приносит свою соль и живёт само по себе. Если это не то, чего вы
хотите, ограничьте:

```json
{ "name": "node-a", "token": "…", "clients": 50 }
```

Считаются **разные машины**, а не соединения. Машина, открывшая тысячу параллельных
сессий, занимает одно место из пятидесяти — иначе лимит резал бы нормальную работу.
Место освобождается, когда с этого адреса закрылось последнее соединение. Клиент сверх
лимита получает отказ, в журнале сервера появляется `отказ node-a: занято мест 50`.

Про лимит стоит помнить ещё вот что: счётчики монитора ведутся **по имени пользователя**,
поэтому несколько машин под одним токеном сольются в одну строку, и отозвать доступ у
одной из них не выйдет — токен общий. Если машины надо различать, заведите им разные
токены, а не поднимайте лимит.

### Применить без разрыва соединений

Пользователей, лимиты и привязки можно применить на живой службе:

```bash
sudo systemctl reload sunfired     # или «Сохранить и применить» в меню
```

Установленные сессии продолжают работать, новые подключения берут свежий список токенов.
Адреса прослушивания, `status_addr` и `transport_key` на ходу не меняются — для них нужен
перезапуск, о чём служба честно скажет в журнал, а всё остальное применит.

TCP и UDP могут висеть на одном номере порта, это разные сокеты. В фаерволе откройте порт
**и по TCP, и по UDP**.

## Запуск

```bash
sudo systemctl enable --now sunfired
journalctl -u sunfired -f
```

| флаг | по умолчанию | что |
|---|---|---|
| `-config` | `/etc/sunfire/main.conf` | путь к конфигу |
| `-menu` | — | открыть меню настройки |
| `-token` | — | напечатать новый токен и выйти |
| `-top` | — | открыть монитор |
| `-version` | — | напечатать версию и выйти |
| `-check-update` | — | проверить наличие новой версии и выйти |
| `-update` | — | обновиться до последней версии и выйти |

# Клиент

## Установка

### Пакет

```bash
curl -LO https://github.com/redsawah/sunfire/releases/latest/download/sunfire_0.3.4_amd64.deb
sudo dpkg -i sunfire_0.3.4_amd64.deb
```

Кладёт `/usr/bin/sunfire`, юнит `/lib/systemd/system/sunfire.service` и пример
`/etc/sunfire/client.conf.example`.

### Из исходников

```bash
git clone https://github.com/redsawah/sunfire && cd sunfire
go build -o sunfire ./cmd/sunfire
sudo install -m755 sunfire /usr/bin/
```

## Настройка

Через `sudo sunfire -menu` либо руками в `/etc/sunfire/client.conf`:

```json
{
  "socks": "127.0.0.1:1080",
  "transport": "auto",
  "streams": 1,
  "servers": [
    { "name": "nl",  "gw": "nl.example:9000",  "token": "…", "transport_key": "…" },
    { "name": "vi1", "gw": "vi1.example:9000", "token": "…" }
  ]
}
```

| поле | что |
|---|---|
| `socks` | адрес локального SOCKS5, только петля. По умолчанию `127.0.0.1:1080` |
| `status_addr` | адрес статуса для монитора, только петля. По умолчанию `127.0.0.1:9602` |
| `transport` | `auto`, `tcp` или `udp` |
| `streams` | соединений на одну сессию, см. ниже |
| `servers[].name` | короткое имя для меню и журнала |
| `servers[].gw` | адрес сервера `host:port` |
| `servers[].token` | токен, выданный сервером |
| `servers[].transport_key` | транспортный ключ сервера. Без него этот сервер доступен только по `tcp` |

### Несколько серверов

Порядок в списке — очередь перехода. На старте клиент берёт первый отвечающий; если тот
перестал принимать подключения, помечает его нездоровым на минуту и уходит на следующий.

Переход происходит не с первой неудачи. На нагруженном плече пакеты теряются, и отдельное
подключение не укладывается в таймаут даже при полностью живом сервере — если реагировать
на каждую такую осечку, клиент будет метаться между серверами вместо работы. Поэтому
сервер считается упавшим только после трёх неудач подряд за двадцать секунд, а любое
удачное подключение обрывает эту череду.

### Про `-streams`

Одно TCP-соединение упирается в потолок маршрута: на канале с потерями и RTT 38 мс это
около 600 Мбит/с, сколько бы ни было свободной полосы. `-streams N` раскладывает **одну**
сессию по N соединениям и собирает обратно на сервере.

Нужно это только когда одна сессия должна забрать канал целиком. Если через плечо и так
идёт много одновременных соединений, они раскладываются сами, и `streams` не нужен.
Больше того, на быстром маршруте раскладка может оказаться **медленнее** одиночного
соединения — сборка идёт в один поток и становится узким местом. Померьте до того, как
включать; по умолчанию `1`.

## Запуск

```bash
sudo systemctl enable --now sunfire
journalctl -u sunfire -f
```

Проверка:

```bash
curl -x socks5h://127.0.0.1:1080 https://ifconfig.me    # должен показать адрес сервера
```

При `transport: auto` клиент меряет каждый транспорт и садится на самый быстрый:

```
замер транспортов до nl.example:9000…
  tcp  842 Мбит/с, rtt 31ms
  udp  1170 Мбит/с, rtt 29ms
сервер nl (nl.example:9000), задержка 29ms
SOCKS5 127.0.0.1:1080 -> nl.example:9000 (udp)
```

| флаг | по умолчанию | что |
|---|---|---|
| `-config` | `/etc/sunfire/client.conf` | путь к конфигу |
| `-menu` | — | открыть меню настройки |
| `-top` | — | открыть монитор |
| `-gw` | — | адрес сервера `host:port`, перекрывает конфиг |
| `-token` | — | токен, перекрывает конфиг |
| `-socks` | `127.0.0.1:1080` | адрес SOCKS5, только петля |
| `-status` | `127.0.0.1:9602` | адрес статуса для монитора, только петля |
| `-transport` | `auto` | `auto`, `tcp` или `udp` |
| `-streams` | `1` | соединений на одну сессию |
| `-probe-time` | `3s` | сколько лить при замере одного транспорта |
| `-v` | выкл | подробный лог |
| `-version` | — | напечатать версию и выйти |
| `-check-update` | — | проверить наличие новой версии и выйти |
| `-update` | — | обновиться до последней версии и выйти |

# Монитор

```bash
sudo sunfired -top     # на сервере
sudo sunfire -top      # на клиенте
```

Шесть панелей: сессии и скорости с нагрузкой машины, график канала отдельно на загрузку и
отдачу, таблица по пользователям (на клиенте — по хостам назначения, видно куда именно
идёт трафик) и лента журнала. График прижат к правому краю и продолжает идти, даже когда
скорость нулевая, — сразу видно, что монитор живой, а не завис.

Данные берутся со статуса, который служба поднимает **только на петле**. Адрес не на петле
конфиг отвергает: наружу это не выставить даже по ошибке.

# Как устроен протокол

Клиент открывает соединение и первым делом шлёт 32 байта случайной соли открытым текстом.
Дальше обе стороны выводят из соли и токена два независимых подключа —
`HKDF-SHA256(token, salt, "sunfire/1 c2s")` и `…s2c`, по одному на направление, чтобы
счётчики-нонсы не пересекались: повтор нонса под одним ключом ломает AEAD полностью.

Сам токен по проводу не идёт. Сервер перебирает свои токены и берёт тот, которым
расшифровался первый кадр, — их единицы, перебор ничего не стоит.

Дальше всё едет кадрами:

```
[ длина полезного (2) + длина набивки (2) | тег ][ полезное + набивка | тег ]
```

Шифр — ChaCha20-Poly1305, один на всех: постоянное время в софте на любой архитектуре, без
зависимости от AES-NI и без согласования шифра по проводу. Нонс — счётчик, свой на каждое
направление. Полезное — до 16 КиБ, кадр уходит одним `Write`: раздельная запись заголовка
гнала бы на провод отдельный крошечный сегмент перед каждыми 16 КиБ.

Набивка идёт нулями и на приёме отбрасывается — после шифрования она всё равно
неотличима от случайного, поэтому случайна только её длина. Первый кадр набивается
заметно, дальше редко и мелко: так размеры кадров не повторяют размеры данных приложения.

Первый кадр от клиента несёт адрес цели, дальше идут данные.

UDP-транспорт даёт надёжный поток через KCP, а каждая датаграмма перед отправкой
запечатывается отдельно — заголовки KCP оказываются внутри шифротекста. Ключ здесь общий
для сервера (`transport_key`), а не выведенный из токена, и это вынужденно: датаграмму
приходится расшифровать раньше, чем станет известно, чей это пользователь. Аутентификация
пользователя как была внутри потока, так и осталась.

При `streams > 1` первый кадр несёт служебную форму `@s <sid> <n> host:port`, остальные
соединения присоединяются кадром `@j <sid> <idx>`. Данные режутся на куски по 64 КиБ и
идут по кругу: кусок k по соединению k mod n, поэтому порядковые номера не нужны — порядок
задаётся позицией.

Замер скорости использует служебный адрес `@probe`: сервер на него никуда не соединяется,
а отражает первую посылку (это RTT) и дальше поглощает поток (это пропускная способность).

# Чего пока нет

- защиты от повтора: записанное начало соединения можно переиграть;
- `UDP ASSOCIATE` в SOCKS5 — поддерживается только `CONNECT`, весь UDP придётся вести
  мимо;
- подписи поверх контрольных сумм в релизах: обновление сверяет sha256, но не подпись.

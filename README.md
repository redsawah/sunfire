# sunfire

Мостовой шлюз. Клиент терминирует SOCKS5 на петле, заворачивает каждую сессию в отдельный
AEAD-поток и уносит на шлюз; шлюз распаковывает поток и открывает соединение к цели уже от
своего адреса. Для цели источник трафика — шлюз.

```
   127.0.0.1:1080                                        exit
        │                                                  ▲
   ┌────┴────┐   salt ‖ ChaCha20-Poly1305 frames    ┌───────┴───────┐
   │ sunfire │ ═══════════ tcp | udp (kcp) ════════ │   sunfired    │
   └────┬────┘                                      └───────┬───────┘
        │ socks5                                            │ dial
   приложение                                             цель
```

Ключи разводятся HKDF-SHA256 по направлениям, токен по проводу не ходит, кадры набиваются
до плавающей длины. Ни TUN, ни root, ни правки маршрутизации — обычный процесс со
слушателем на петле.

Одна SOCKS-сессия — одно соединение до шлюза, без мультиплексора: нагрузка сама
раскладывается по ядрам. Транспорта два, TCP и UDP поверх KCP; клиент умеет замерить оба и
сесть на тот, что быстрее на этом маршруте.

## Установка

### Пакеты

```bash
sudo dpkg -i sunfired_0.1.0_amd64.deb    # шлюз
sudo dpkg -i sunfire_0.1.0_amd64.deb     # клиент
```

Пакет кладёт бинарь в `/usr/bin`, unit в `/lib/systemd/system` и пример конфига в
`/etc/sunfire`. Собрать пакеты самому:

```bash
sh scripts/build-deb.sh 0.1.0
```

Готовые файлы появятся в `dist/`.

### Из исходников

Нужен Go 1.26+.

```bash
git clone https://github.com/redsawah/sunfire
cd sunfire
go build -o sunfired ./cmd/sunfired
go build -o sunfire  ./cmd/sunfire
sudo install -m755 sunfired sunfire /usr/bin/
```

## Шлюз

Токен на каждого клиента:

```bash
sunfired -token
```

`/etc/sunfire/main.conf`:

```json
{
  "listen": {
    "tcp": ":9000",
    "udp": ":9000"
  },
  "users": [
    { "name": "node-a", "token": "ВАШ-ТОКЕН", "allow_ips": ["203.0.113.7"] }
  ]
}
```

TCP и UDP могут висеть на одном номере порта — это разные сокеты. В фаерволе откройте порт
и по TCP, и по UDP.

### В докере

Положите `main.conf` рядом с `docker-compose.yml`:

```bash
docker compose up -d
docker compose logs -f
```

Конфиг пробрасывается томом, так что правится снаружи контейнера:

```yaml
volumes:
  - ./main.conf:/etc/sunfire/main.conf:ro
```

Сеть хостовая: `allow_ips` сверяется с реальным адресом клиента, а за NAT контейнера все
подключения выглядели бы как один адрес.

Образ собирается под ту архитектуру, где вы его собираете. Если собираете на arm-машине, а
шлюз поедет на x86-сервер:

```bash
docker build --platform linux/amd64 -t sunfire/sunfired .
```

### Без докера

```bash
sudo systemctl enable --now sunfired
journalctl -u sunfired -f
```

## Клиент

```bash
sunfire -gw ШЛЮЗ:9000 -token ВАШ-ТОКЕН -socks 127.0.0.1:1080
```

Проверка:

```bash
curl -x socks5h://127.0.0.1:1080 https://ifconfig.me
```

По умолчанию `-transport auto`: клиент прогоняет замер по каждому транспорту и садится на
самый быстрый.

```
замер транспортов…
  tcp  842 Мбит/с, rtt 31ms
  udp  1170 Мбит/с, rtt 29ms
SOCKS5 127.0.0.1:1080 -> ШЛЮЗ:9000 (udp)
```

Автозапуск: впишите адрес и токен в `/etc/sunfire/client.env` и включите unit.

```bash
sudo systemctl enable --now sunfire
```

## Параметры

Клиент:

| флаг | по умолчанию | что |
|---|---|---|
| `-gw` | — | адрес шлюза `host:port` |
| `-token` | — | токен |
| `-socks` | `127.0.0.1:1080` | адрес SOCKS5, только петля |
| `-transport` | `auto` | `auto`, `tcp` или `udp` |
| `-probe-time` | `3s` | сколько лить при замере одного транспорта |
| `-v` | выкл | подробный лог |

Шлюз:

| флаг | по умолчанию | что |
|---|---|---|
| `-config` | `/etc/sunfire/main.conf` | путь к конфигу |
| `-token` | — | напечатать новый токен и выйти |

## Конфиг шлюза

| поле | что |
|---|---|
| `listen` | транспорт → адрес. Ключи только `tcp` и `udp`, хотя бы один |
| `users[].name` | имя, обязательное и непустое |
| `users[].token` | токен, минимум 16 символов, не повторяется между пользователями |
| `users[].allow_ips` | с каких адресов принимать: IP и/или подсети `10.0.0.0/8`. Пусто или нет поля — отовсюду |
| `users[].disabled` | выключить, не удаляя |

Конфиг читается один раз при старте — после правки перезапустите шлюз.

## Как устроен протокол

Одно SOCKS-соединение — одно соединение к шлюзу, без мультиплексора.

Клиент открывает соединение и первым делом шлёт 32 байта случайной соли открытым текстом.
Дальше обе стороны выводят из соли и токена два независимых подключа —
`HKDF-SHA256(token, salt, "sunfire/1 c2s")` и `…s2c`, по одному на направление, чтобы
счётчики-нонсы не пересекались. Сам токен по проводу не идёт: шлюз перебирает свои токены
и берёт тот, которым расшифровался первый кадр.

Дальше всё едет кадрами:

```
[ длина полезного (2) + длина набивки (2) | тег ][ полезное + набивка | тег ]
```

Шифр — ChaCha20-Poly1305, нонс — счётчик, свой на каждое направление, инкремент на каждый
кадр (заголовок и тело считаются отдельно). Полезное — до 16 КиБ. Набивка идёт нулями и
на приёме отбрасывается: первый кадр набивается заметно, дальше редко и мелко, чтобы
размеры кадров не повторяли размеры данных приложения.

Первый кадр от клиента несёт адрес цели, дальше идут данные.

UDP-транспорт даёт надёжный поток через KCP, а каждая датаграмма перед отправкой
запечатывается отдельно: ключ — `HKDF-SHA256(token, "sunfire/1 udp")`, нонс — 12 случайных
байт перед шифротекстом. Заголовки KCP оказываются внутри шифротекста. Битые и чужие
датаграммы молча отбрасываются.

Замер скорости использует служебный адрес `@probe`: шлюз на него никуда не соединяется, а
отражает первую посылку (это RTT) и дальше поглощает поток (это пропускная способность).

## Чего пока нет

- защиты от повтора: записанное начало соединения можно переиграть;
- ограничения на число одновременных соединений с одним токеном;
- UDP ASSOCIATE в SOCKS5 — поддерживается только CONNECT.
